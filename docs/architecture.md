# 아키텍처

## 구성 요소

세 개의 역할이 있다.

- **Host** — 프로젝트 등록(`Projects`), 검사 신청서·분석 요청 접수, 검사 결과서와 프로젝트 모델 저장을 담당하는 중앙 서비스.
- **Worker** — 실제 실행 환경(개발 머신 등)에서 에이전트를 구동해 검사를 수행하는 실행 노드. 다른 실행 환경으로 확장될 수 있으나, 지금은 웹/서버 지원만 구현하며 그 확장을 위한 추상화 레이어를 미리 만들지 않는다.
- **Console** — Host API의 클라이언트인 관리자 UI. 별도의 특권 경로를 갖지 않는다.

## 연결 방향

Worker가 Host에 접속한다(pull). Host가 Worker에 직접 접속하지 않는다. 이 방향 덕분에 방화벽 뒤 사내망에 있는 실행 환경도 문제없이 연결된다. Worker 전용 엔드포인트(claim/report/fail, 프로젝트 모델 제출)는 공유 키 기반 인증으로 보호된다 — 설정은 [README](../README.md) 참고.

## 데이터 소유권

소스 코드, 실행 로그, 스크린샷 등 검사 중 생성되는 원본 데이터는 Worker(실행 환경 로컬)에 남는다. Host는 검사 결과서(판정·요약·근거 텍스트)만 수신하고 저장한다. Host에 원본 코드가 집중되지 않는다.

Host는 검사 결과서 + 프로젝트 모델 + 프로젝트 지식(선언의 연장인 문서·히스토리 인덱스)을 저장한다. 프로젝트 모델의
정본은 Host 데이터베이스이고, 지식 인덱스에 들어간 모델 진술은 거기서 파생된 사본이다. 원본 실행
아티팩트(스크린샷·로그 등)만 Worker 로컬에 남고 비영속적이다(워커풀 전제상 요청마다 폐기될 수
있다).

## 핵심 산출물 모델

- **검사 신청서(입력)** — 매 검사 실행마다 제출하는 가벼운 요청. 무엇을 검사할지에 대한 트리거다.
- **프로젝트 선언** — 목적·비전·범위·경계에 대한 선언. Host의 `Projects` 엔티티에 등록되며, 신청서보다 훨씬 드물게 바뀐다. 대상 리포 안에는 아무것도 두지 않는다(비침습성) — 대상 리포에 어떤 파일도 없이 Momos가 작동할 수 있다.
- **검사 결과서(출력)** — 실행 결과와 근거 있는 지적을 담은 리포트.
- **분석 요청(입력)** — 프로젝트 모델을 만들라는 요청. 검사 신청서와 같은 큐에 들어가며 종류(`Kind`)로만 구별된다.
- **프로젝트 모델(출력)** — 한 커밋 시점의 프로젝트 설계 이해. 구성 요소·관계·패턴·결정·의도·흐름·불변식과,
  그것을 뒷받침하는 등급·근거가 붙은 진술(claim), 리포트의 장 구성(목차), 분석 범위(무엇을 읽고 무엇을 읽지 않았나)로
  이뤄진다. 분석할 때마다 새 버전이 만들어진다.

## 프로젝트 모델

분석 요청은 검사 신청서와 같은 큐를 쓴다. Worker는 `claim-next`로 요청을 가져올 때 종류를 함께 받고, 대상 리포를
같은 방식으로 체크아웃한 뒤 종류에 따라 갈라진다 — 검사는 에이전트 루프를 돌리고, 분석은 결정적 추출기를 돌린 뒤
그 위에서 언어 모델 패스를 돌린다. 추출기는 체크아웃한 커밋의 .NET 프로젝트 파일(`*.csproj`)을 읽어 프로젝트를 구성 요소로,
프로젝트 참조를 관계로 만들고, 각각을 근거(프로젝트 파일 경로, 참조라면 그 줄)가 붙은 `Fact` 진술로 뒷받침한다. 이어서
구성 요소마다 읽기 전용 git 명령(`rev-list`·`log`)으로 변경 이력을 세어 커밋 sha가 근거인 `History` 진술을 더한다. 읽은 것과
읽지 않은 것(읽지 못한 프로젝트 파일, 소스 코드, .NET이 아닌 빌드)은 분석 범위로 함께 기록된다.

언어 모델 패스는 개관 1회(장 구성과 프로젝트가 밝힌 의도)와 장마다 1회다. 패스마다 새 에이전트 루프가 체크아웃을 읽고
제안 도구로만 모델을 바꾼다 — 지적을 보고하는 도구는 없다. 제안은 들어오는 즉시 모델 규칙과 근거 검사를 거친다: 근거는
**분석한 커밋의 git 객체**에서 확인한다(코드 경로와 그 안에 글자 그대로 있는 기호, 이력 안의 커밋, 리포나 커밋 메시지에
나오는 PR·이슈 URL — 네트워크 없음). 에이전트가 체크아웃에 쓴 파일은 근거가 되지 않는다. 통과한 제안만 `Synthesized`
진술·요소로 남고, 기각은 사유별 건수로 분석 범위에 기록된다. 패스는 끝나야 반영된다 — 토큰·시간 예산이 떨어지거나 모델
호출이 실패한 장은 통째로 빠지고 그 이유가 분석 범위에 남으며, 분석은 나머지로 완료된다. 추출이 실패하면 검사와 같은
실패 보고 경로로 보고된다.

```
분석 요청 ──> [같은 큐] ──claim-next──> Worker ──체크아웃──> 추출기
                                                              │ 모델 제출
                                                              v
개발자 ──교정──> Host DB (모델 정본) ──투영──> 지식 인덱스 (파생) <──지식 조회── 검사 에이전트
   ^                 │
   └── 딥 리포트 <────┘
```

- **정본과 파생** — 제출된 모델은 Host 데이터베이스에 저장되고 곧바로 응답한다. 지식 인덱스는 백그라운드
  서비스가 따라잡는다 — 모델이 인덱스에 반영되지 않은 동안 이 서비스가 모든 진술이 인덱스에 들어갈 때까지 재시도하고,
  다 들어가면 `knowledgeIndexedAt`을 기록한다. 최신 분석에서 사라진 진술은 인덱스에서도 지워진다. 인덱스가
  실패해도 저장된 모델은 그대로이고, 인덱스 호출은 직렬화된다. 업그레이드 뒤 첫 Host 기동은 모든 프로젝트의 최신
  모델을 한 번씩 다시 색인한다(기존 모델에는 `knowledgeIndexedAt`이 없다) — 임베딩 호출이 한꺼번에 몰릴 수 있다.
- **교정 루프** — 개발자가 진술을 확인·반박·교정하면 그 판정이 진술 옆에 기록되고(진술 자체는 고쳐지거나 지워지지
  않는다) `knowledgeIndexedAt`이 null로 되돌려져 최신 모델이 다시 색인된다. 검사 에이전트는 기존 지식 조회 도구로 모델 진술과 교정을 함께 읽으며,
  교정이 있으면 그것을 의도된 설계로 보고 동작을 판단한다. 모델 진술은 검사의 맥락일 뿐 근거가 아니다 — 지적은
  여전히 그것을 재현한 명령 출력을 근거로 가져야 한다.
- **버전** — 분석할 때마다 새 모델 버전이 만들어진다(증분 분석·중복 제거는 아직 없다). 개발자의 판정은 재분석된
  진술의 문장이 이전과 똑같을 때만 새 버전으로 이어지고, 문장이 달라지면 `Proposed`로 다시 시작한다.
- **딥 리포트** — 최신 모델을 개발자가 읽는 마크다운 문서 트리로 렌더링한 것. 모든 문장은 진술로 거슬러 올라가고,
  개발자의 판정은 원래 진술을 대신하지 않고 그 옆에 함께 표시된다. 장 구성은 모델의 목차를 따르고(없으면 고정
  레이아웃), 렌더러는 배치만 할 뿐 새 주장을 만들지 않는다. 이 리포트가 모르는 것(`unknowns.md` — 읽지 않은 영역,
  이유가 기록되지 않은 결정, 판정되지 않은 해석)은 생략되지 않는 페이지다.

## 통합 방식

대부분의 액션은 API로 이뤄진다. Console도 그 API의 클라이언트일 뿐이다. Momos는 개별 이슈를 자체적으로 추적하지 않으며, 후속 조치가 필요한 지적은 docket 또는 GitHub Issues로 넘긴다.

## 에이전트 실행

Worker의 에이전트는 샌드박스 작업 공간에서 명령을 실행하는 도구(빌드·테스트·스크립트 등 리포가 제공하는 것을 그대로 돌린다), 프로젝트 지식 검색 도구, 재현 근거가 붙은 지적을 기록하는 도구를 상황에 맞게 오케스트레이션한다. 도구 호출은 MCP(Model Context Protocol) 표준을 따른다. Computer Use(화면을 보고 직접 조작하는 능력)는 설계상 목표이지만 **아직 활성화되지 않았다** — 현재 에이전트는 화면을 다루지 않는다.

## 라이선스와 공개 경계

`momos`는 AGPL-3.0으로 공개된다. 코드베이스는 단일하며, 별도의 비공개 확장 리포는 (지금은) 두지 않는다.
