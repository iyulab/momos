# Momos 헌법

## 1. 정체성과 철학

Momos는 정적 분석이 잡지 못하는 실행 환경의 문제 — 실제로 실행해봐야 드러나는 UX 흐름의 결함, 실행 중 발견되는 버그 — 를 자율 에이전트가 직접 상호작용하며 찾아내는 도구다.

이름은 그리스 신화 속 조롱과 비평의 신 모모스(Μῶμος)에서 왔다. 어떤 결과물도 완전히 만족하지 않고 계속 문제를 제기하는 높은 품질 기준을 의인화한 이름이다.

### 핵심 가치

1. **근거 기반 엄밀함 (비타협)** — 근거 없는 지적은 내놓지 않는다. 확신이 없으면 침묵한다.
   - *비싸지는 순간*: 애매한 영역에서는 말을 아끼게 되어, 겉보기엔 덜 엄격해 보일 수 있다.
2. **실행 범용성** — 웹이든 데스크톱이든, 같은 메커니즘(에이전트 + Computer Use)으로 폭넓게 다룬다.
   - *비싸지는 순간*: 특정 분야의 깊이는 그 분야 전문 도구보다 낮을 수 있다.
3. **지속적 동반자성** — 커밋마다 막아서는 게이트가 아니라, 개발 기간 내내 함께하는 존재다.
   - *비싸지는 순간*: 실시간 게이트로 쓰기엔 부적합하고, 초반 결과가 얕아 보일 수 있다.
4. **업스트림 우선주의** — 이미 있는 좋은 도구(iyulab 생태계 포함)를 재구현하지 않고 그 위에 확장한다.
   - *비싸지는 순간*: Momos의 개발 속도가 상위 리포의 대응 속도에 종속될 수 있다.
5. **보안성/격리 최우선** — 자율 에이전트가 실제 시스템(Computer Use)을 조작하므로, 다른 어떤 품질 속성보다 안전한 격리가 우선한다.
   - *비싸지는 순간*: 격리를 강하게 하면 새 도구·환경을 유연하게 붙이기 어려워진다.

### 비목표 (Non-goals)

- 코드를 자동으로 고치지 않는다 — 발견·보고·이슈화까지만 한다.
- 실제 인증(GS인증, CC인증 등) 절차를 대행하지 않는다.
- 요구사항의 사업적 타당성(시장성, 우선순위)을 판단하지 않는다 — 선언된 목적·비전의 *내적 일관성*은 다루되, 그 비전이 사업적으로 좋은 선택인지는 다루지 않는다.
- 자체 이슈 트래킹 기능을 제공하지 않는다 — 후속 조치는 docket 또는 GitHub Issues에 위임한다.

## 2. 범위 경계

### 지금 다루는 것 (In)
- 웹/서버 기반 프로젝트의 실행 테스트
- 기능적 결함(실행 중 발견되는 버그·깨진 흐름)
- 사용성/UX 컨벤션 정합성(근거 있는 비평)
- 선언된 목적·비전과 구현의 내적 정합성 검토

### 나중에 다룰 것 (Later)
- 데스크톱 GUI 앱 실행 테스트
- 체계적인 전문 보안 점검 (단, 실행 중 우연히 발견한 명백한 위험은 지금부터 보고한다 — 이건 "later"의 예외다)
- `momos-console`(관리자 UI)의 본격적인 기능

### 과잉의 판별 기준
"이 능력을 처음 쓰는 제3의 소비자가 같은 자리에서 같은 재구현을 하게 되는가?" — 그렇다면 이 리포의 몫이다. 특정 소비자만의 도메인 지식이 있어야 필요한 것이라면 범위 밖이다.

## 3. 품질 기준

### 설계 원칙 (Momos 자신의 코드)
- 트레이드오프 서열: **안정성 > 가독성/단순함 > 개발속도 > 호환성 > 성능**. 0.x 단계이므로 호환성을 지키려고 이 서열을 뒤집지 않는다.
- 구현 스택은 .NET 단일 스택(Host/Worker 공통)이다.
- 에이전트/도구 오케스트레이션은 MCP(Model Context Protocol) 표준을 따른다. 자체 프로토콜을 발명하지 않는다.
- Computer Use 관련 코드는 항상 격리·보안을 최우선으로 설계한다. 위협 분류와 대응 원칙은 [threat-model.md](threat-model.md) 참고.

### 판단 원칙 (Momos가 타겟 프로젝트를 평가할 때)
- 판단 전 반드시 타겟 프로젝트가 선언한 목표·비전·범위·경계를 이해하고, 그 틀 안에서 평가한다.
- 목표의 내적 정합성(선언된 비전과 실제 구현의 모순)은 비판하되, 사업적 타당성은 비판하지 않는다.
- 범위·경계 자체를 좁히거나 넓히자는 제안은 리서치 근거 없이 하지 않는다.
- 체계적 보안 점검(범위 밖)과 별개로, 실행 중 우연히 발견한 명백한 위험은 항상 보고한다.

## 4. 개선 프로토콜

| 등급 | 범위 | 보고 형식 |
|---|---|---|
| 자율 수행 | 버그 수정, 테스트 추가, 내부 리팩터링, 문서 정리 | 커밋 메시지 |
| 제안 후 승인 | 공개 API 변경, 의존성 추가, 데이터 스키마 변경 | 변경 전 계획 제시 + 승인 대기 |
| 반드시 논의 | 원칙 위반, 비목표 침범, Type-1 재결정, **Computer Use 권한/격리 설정 변경(예외 없음)** | 이슈 초안 작성 + 사람과 논의 |

## 5. 감사 체크리스트

- [ ] 이번 변경이 근거 기반 엄밀함 원칙을 위반하지 않는가
- [ ] Computer Use 권한/격리 관련 변경이 "반드시 논의" 절차를 거쳤는가
- [ ] 비목표(자동수정·인증대행·사업판단·자체이슈트래킹)를 침범하지 않는가
- [ ] 트레이드오프 서열(안정성 > 가독성 > 개발속도 > 호환성 > 성능)에 맞는가
- [ ] 타겟 리포에 어떤 흔적도 요구하지 않는 비침습성을 지키는가

## 6. 진화 방향

v1(웹/서버, 기능적 결함 + UX 정합성)에서 시작해, 검증되는 대로 데스크톱 실행 지원과 전문 보안 점검 축으로 확장한다. 장기적으로는 인증기관이 참고할 만한 엄밀함을 지향하되, 인증기관 역할 자체를 대행하지는 않는다.

## 7. 개정 절차

이 헌법의 Type-1 항목(정체성, 비목표, 시스템 경계, 라이선스, 성공 지표)을 바꾸려면 반드시 사람과의 논의를 거친다(4절 "반드시 논의" 등급). 변경이 확정되면 이 문서를 현재형으로 다시 쓰고, 검토 과정과 근거는 이 리포 밖의 비공개 결정 기록에 남긴다.
