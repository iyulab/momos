상태: 이 문서는 v1 범위의 위협 분류와 대응 원칙을 기술한다. 격리 메커니즘의 기술적 구현(프로세스/컨테이너/VM 등)은 이 문서의 범위 밖이다.

# 위협 모델

Worker의 에이전트는 Computer Use(화면을 보고 직접 조작하는 능력)를 통해 실제 시스템에 작용한다. 이 문서는 그 실행이 만들어내는 위협을 분류하고, v1에서 어떤 원칙으로 대응하는지를 정한다.

## 신뢰 경계

- **검사 대상(target-under-test)은 비신뢰 입력이다.** 대상 프로젝트의 코드, 에러 메시지, 화면에 표시되는 텍스트는 모두 잠재적으로 에이전트를 오도하려는 입력으로 취급한다.
- **LLM의 출력은 비신뢰다.** 에이전트가 스스로 내린 판단(“이 명령을 실행하면 해결된다” 등)도 검증 없이 그대로 실행하지 않는다. 신뢰는 판단의 근거(대상이 무엇을 선언했는가)에 있지, 판단을 내린 모델 자체에 있지 않다.
- **Worker 머신은 신뢰 환경으로 취급한다.** 사용자가 통제하는 실행 환경이라는 전제 위에서 설계한다. Worker 자체가 이미 손상된 상태를 가정하는 설계(제로 트러스트)는 v1 범위 밖이며, 격리 메커니즘이 실제로 도입되는 시점에 재검토한다.

## 위협 시나리오

### 1. 검사 대상발 공격

대상 프로젝트의 화면 텍스트, 에러 메시지, 파일 내용 등을 통해 에이전트에게 의도치 않은 행동을 유도하는 경우(예: 프롬프트 인젝션). 대상이 악의적이지 않아도, 우연히 오해를 유발하는 문구만으로도 발생할 수 있다.

### 2. 에이전트의 자율 오동작

대상이 무해하고 공격자가 없어도, 에이전트가 스스로 잘못 판단해 파괴적 행동(파일 삭제, 설정 변경, 외부 서비스로의 의도치 않은 요청 등)을 실행하는 경우. 실무에서 가장 흔하게 발생할 가능성이 높은 시나리오다.

### 3. Worker 손상 시 확산

위 두 경로로 Worker가 손상되더라도, 그 피해가 Worker 바깥으로 번지지 않도록 하는 구조가 이미 아키텍처에 내장돼 있다.

- Worker가 Host에 접속하는 pull 연결 구조([architecture.md](architecture.md))는 Host가 Worker에 직접 접근할 경로를 애초에 만들지 않는다 — Worker가 손상돼도 Host로의 역방향 침투 표면이 없다.
- 원본 코드·로그·스크린샷이 Worker 로컬에만 남고 Host는 검사 결과서만 받는 데이터 소유권 구조([architecture.md](architecture.md))는, Worker가 손상되더라도 다른 프로젝트의 원본 데이터가 함께 유출되지 않게 한다.

## v1 대응 원칙

- **파괴적 행동은 사전 확인을 거친다.** 파일 삭제, 데이터 전송, 패키지 설치, 시스템 설정 변경 등 되돌리기 어려운 행동을 에이전트가 실행하려 할 때는, 그 전에 반드시 사람의 확인을 받는다. 이 규칙에는 예외를 두지 않는다.
- **근거 없는 판단은 행동으로 옮기지 않는다.** 위 신뢰 경계에 따라, 에이전트가 화면이나 코드에서 읽은 내용을 곧바로 파괴적 행동의 근거로 삼지 않는다.
- **우연히 발견한 위험은 즉시 보고한다.** 체계적인 보안 점검은 v1 범위 밖이지만, 검사 도중 우연히 발견한 명백한 위험(예: 노출된 자격증명)은 v1부터 보고 대상이다.

## 범위 밖

- 격리 메커니즘의 기술적 구현(프로세스 샌드박싱, 컨테이너, VM 등 무엇으로 격리할지) — 별도 논의 대상.
- 유출 경로에 대한 체계적 보안 점검 — Later 범위.
- Worker 머신 자체가 손상돼 있다고 가정하는 설계(제로 트러스트) — 격리 메커니즘 도입 시 재검토.
